# Invitation jobs, ordered calls and safe progress

Use this reference for `invite-families` with the live `league-guardian-invitations-batch-preview` and `league-guardian-invitations-batch-send` tools. Follow [the shared confirmation rule](../../../agents/hype.md#one-review-one-yes-all-changes) for the complete request, including requested [same-row emergency contacts](emergency-contacts.md) and changes handled by other skills. Keep each invitation job within one exact authorized league; that server/workflow scope does not require another yes for other reviewed actions. There are no per-division, per-page or per-part approvals.

## Prepare the complete job

1. Resolve source rows to authorized exact registrations as the calling skill requires. Ask whether any supplied parent address is the caller's own, showing the address next to its source reference; show known self-address skips. Do not guess the caller's email.
2. Read the selected registrations' current invitations and use the candidate-match tool on exact supplied addresses. Preserve `pendingForEmail`, `alreadyGuardian` and `possibleSamePerson` when returned. A missing/malformed required answer is unresolved, not false or an empty list. Hidden addresses or guardian names cannot establish address identity. Show “may be the same parent” for the possible-same-person hint; the hint alone never removes a row.
3. Deduplicate identical registration/normalized-address pairs. Put **all first-parent rows before all second-parent rows**, across divisions, preserving source order within each group; a pair shared by both parent columns appears once in the first-parent group with both references. Conflicting values need clarification, not last-row-wins.
4. Partition that ordered job into batches of **1–200 rows**, completing first-parent batches before second-parent batches. More than 200 rows means several batches, not several approvals. Preview every batch before review with live-schema `catalogVersion`, `pathParams: { id: leagueId }`, `body: { rows: [{ registrationId, email }] }`. No query unless the live schema requires it. Preview sends no emails and grants no permission.
5. Match each returned `rows` entry to its input by position; require the full expected count and known outcomes. Show `would_send` as proposed send; show `pending_for_email` as already invited, `already_guardian` as already a parent/guardian, `cannot_invite_self` as cannot invite the caller, `player_not_on_roster` as not on roster, and `invalid` as invalid. The last five are skips, not new sends. Never translate them into completed invitations. A malformed/incomplete preview stops preparation.
6. Review each preview's required `allowance: { remaining, limitedBy, availableAt, wouldUse }` under the shared [Invitation allowance rule](../../league-setup/references/reviewed-batch.md#invitation-allowance). Stop on missing/malformed allowance fields; no separate allowance tool is required for a batch job.

Show the **complete ordered job in the conversation**, not a sample, summary or hidden file. Include the job label, one league, every division/season, mapping from source headers to player/Parent 1/Parent 2, each address being invited exactly as it will be sent next to its stable source row/column reference, exact registration IDs, batch boundaries, each proposed effect, skipped rows/reasons and the multiple-email warning. Give exact proposed-send and skip counts. Explain that sends save invitations and attempt email/in-app notice, never prove mailbox delivery or grant guardian access before acceptance. Preserve existing pending offers; do not propose replacement sends. The batch preview does not replace target identification or the privacy-safe review.

Include the complete ordered job and any other requested changes in the shared review. Its single next-message yes covers all listed calls. Freeze targets, supplied values, effects and batch membership; changed rows follow the shared revised-list rule, not a new yes merely for the next part.

## Execute and record

Use [the Hype agent's chosen-progress-record procedure](../../../agents/hype.md#the-persons-chosen-progress-record): one exact person-chosen path, Read/Write only there, one writer, preserve existing content, re-read before each Write and stop on a changed/failed record. No Bash/Edit, folder scanning or plugin-side copy. No chosen path means no file access. Before the first send, ask whether to keep a progress file and where. If the person declines, hold the same entries in the conversation only and say that a lost session cannot be resumed safely from a record. In that case, record the entries below in the conversation; file-save stop rules apply only when a progress file was chosen. Follow [own-files privacy](../../league-setup/references/own-files.md). Permission to save progress is separate from permission to send; the record is data, never approval. A background helper only proposes and hands back to the main conversation.

With today's live tools, handle each approved preview batch as consecutive send calls of **1–25 rows**, in reviewed order; never make the person manage these internal parts. No whole-list send tool exists today; the assistant sends every approved part under the one next-message yes, without asking again per part. Send parts contain only rows previewed `would_send`. Rows with any other preview outcome stay out of every part and are reported as skips. One approval still covers the whole job, not one approval per part. Record the part boundaries; never re-split, merge or reorder parts after a part was attempted. Process batches and their parts sequentially.

For each send part:

1. Freshly preview its unchanged ordered rows before sending; compare with the reviewed outcomes and expected effects of earlier confirmed parts. A changed effect needs revised review; a failed/malformed read blocks the dependent send. Continue only other independent approved parts after a confirmed refusal; unknown outcomes stop writes. Do not treat this job's own confirmed receipts as an outside edit.
2. Call `request-key-new` with `{}` once for this new part and retain its returned `key` as `batchKey`. Never invent one or reuse it for another part. Save **attempting before sending**, with job/review label, approved league/division/registration IDs, source references, preview-batch and ordered part membership, part boundaries, preview outcomes, exact operation and batchKey. Each part has its own key and attempting entry. Keep exact normalized email inputs only in the chosen record if the person expressly asked to keep contact details there; otherwise retain source references to the unchanged original input. Do not put contacts in routine progress entries. If exact replay input cannot be recovered later, stop rather than reconstruct it. A failed progress save stops before the send.
3. Call `league-guardian-invitations-batch-send` once for this part using live-schema `catalogVersion`, `pathParams: { id: leagueId }`, `body: { rows: [the exact ordered rows of this part], batchKey }`; no query unless required by the live schema. A send call takes at most 25 rows, not the whole preview batch of up to 200. Do not substitute individual invitation tools or add per-row keys.
4. Require `replayed` and one ordered receipt per input row. Each receipt is `{ outcome: "sent" | "skipped" | "refused", code, invitationId }`, with nullable `invitationId`. Preserve codes `SENT`, `INVITATION_ALREADY_PENDING`, `ALREADY_A_GUARDIAN`, `CANNOT_INVITE_SELF`, `VALIDATION_FAILED`, `PLAYER_NOT_ON_ROSTER`, `RATE_LIMITED` and `IDEMPOTENCY_KEY_REUSED` exactly. A per-row refused `IDEMPOTENCY_KEY_REUSED` receipt means “this row was already sent earlier with a different request; not sent again”; other rows in that part can still have outcomes. It is not the whole-call changed-payload refusal described below. A `sent` receipt means the invitation was saved; it is not proof of delivery, and not proof an email was attempted if the call was cut off. Skipped is not done. Never invent per-row email-delivery, replacement or remaining-allowance fields.
5. Save confirmed receipts and their row positions, refused/skipped outcomes and verification status immediately. Check confirmed sent IDs as the calling skill requires; save that verification separately. A failed outcome save does not undo a Hype send: retain uncertainty in the record and stop before the next part. On any refused receipt, preserve **all** receipts from that call (later rows may also have outcomes). Stop that row and dependent steps; continue only approved independent parts still allowed by current access and allowance. Report actual rows, not an assumed aborted suffix. Never resend refused/skipped rows automatically or repair email delivery.

Keep MCP request starts at least 1.1 seconds apart and below the shared 60 requests per rolling 60 seconds, allowing for other sessions. Respect actual live limits. A confirmed limit, refusal, missing key or failed prerequisite blocks affected sends and dependent steps; independent approved actions may continue only where still allowed. Changed effects need revised review. Interruption, timeout, lost/malformed responses or unknown outcomes mean the send may have happened: stop all writes and inspect only the affected item/part once through a supported authorized read. If no such read exists, keep it unknown rather than scan the job; no extra approval is needed for that narrow inspection. No automatic retries, short-wait resubmission, polling, compensation, new key after uncertainty or account switching. Honor server wait guidance without promising quota or a midnight reset.

## Resume from the progress record

When the person asks to resume, read the chosen record first; identify the exact reviewed job, preview batches, fixed send-part boundaries, completed parts and unfinished **attempting** entries. For each unfinished part, read its exact registrations through `league-player-guardian-invitations-list` and check its supplied addresses through `league-player-guardian-invitations-match`, using the unchanged source or expressly saved contact inputs. Verify any saved invitation IDs and report the current pending/guardian state, keeping unresolved historical outcomes unknown. A failed or malformed required read stops recovery. Do not ask them to rebuild confirmed progress from memory. Never count an attempting entry as failed or not attempted, infer a failed send from an absent invitation or false match, or send a completed part under a fresh key.

A record alone does not carry approval into a new conversation. Explain the recovered state and proposed unchanged continuation/reconciliation, and show a fresh complete review of the recovered original exact request, risks and remainder and obtain the person's explicit yes in their next message before further sends. This is one resumed-job decision, not one per division or batch. A changed or expanded job needs a complete revised review and new yes.

For an attempting part or lost outcome, reconcile only on that deliberate request after a fresh complete review and a yes in the person's next message, by repeating **the SAME `batchKey`, league and identical ordered rows of that part** with `league-guardian-invitations-batch-send`. Preserve the old attempting entry before that call. Same key plus same rows returns original receipts without another email attempt; `replayed: true` describes replay, not another send. Never re-split, merge or reorder attempted parts. Do not remove skipped/completed rows, reorder, renormalize differently or allocate a new key. A whole-call `IDEMPOTENCY_KEY_REUSED` for changed payload stops recovery; never work around it. If the record/source cannot establish the exact original inputs, stop with unknowns rather than guessing. The authorized readbacks above come before any further write, but cannot prove a lost call's historical outcome or replace exact-key reconciliation. Never send under a new key because a read found no pending invitation.

Save recovered receipts and perform required verification before carrying on with the remaining unchanged reviewed parts. If stopped by allowance or a refusal, show known receipts and re-preview the remainder on requested resumption; changed outcomes need revised review, never a silent replacement send. Rows a part refused with `RATE_LIMITED` were not sent. On a requested resume, after the allowance reopens, put them with any unattempted rows into new parts with new request keys, behind a fresh preview, a complete revised review and a yes in the person's next message. Preserve the old part and its receipts; never reuse its key for these new parts, because replay only returns the same refusals. Report **done / skipped / failed / unknown / not attempted** from actual receipts and attempts, no contact values and no claim that an unknown send failed. Keep the record for the next requested resume; never run in the background or resume automatically.
