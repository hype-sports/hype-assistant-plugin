# Invitation jobs and safe progress

Use `league-guardian-invitations-start`, `league-guardian-invitations-progress` and `league-guardian-invitations-cancel` with their discovered live schemas. Follow [the shared confirmation rule](../../../agents/hype.md#one-review-one-yes-all-changes) for the complete request, including requested [same-row emergency contacts](emergency-contacts.md) and other skills. One job stays within one exact authorized league; a Division Admin is limited to one reviewed division and its authorized delivered roster spots. Only the person who started a job can read its progress or cancel it. Never split a list to work around scope or a refusal.

## Prepare and review the complete list

1. Resolve supplied source rows to exact authorized registrations as the calling skill requires. Recipients come only from the person's supplied input, never stored contacts or account searches. Ask about any known self-address ambiguity rather than guessing the caller's email.
2. Deduplicate identical normalized registration/address pairs, retaining every source reference. Keep siblings on different registrations separate. Put **all Parent 1 rows before all Parent 2 rows**, preserving source order within each slot; a pair shared by both columns appears once in slot 1 with both references. Conflicting values need clarification, not last-row-wins.
3. Keep `{ registrationId, email, parentSlot }` for each row, with `parentSlot` exactly `1` or `2`. Start requires at least one row; an empty list needs no key or start. Freeze the exact reviewed values and order. For a Division Admin, also resolve the one `divisionId` and each selected authorized delivered roster spot's `entryId`; if those cannot be established, stop, never guess or substitute another ID type. A league-wide role label grants no additional rights.
4. Do **not** run invitation batch previews, candidate-match calls or per-registration invitation readbacks for this job. Hype checks pending invitations, existing guardians, self-invites, duplicates, roster eligibility, current authority and limits. These checks may be deferred; do not claim every proposed invitation is sendable before the job reports it. No per-recipient key or assistant-side send loop is needed.

Show the **complete ordered list in the conversation**, not a sample or hidden file: job label, league, divisions/seasons, source-column mapping, stable source-row/Parent 1/Parent 2 labels, exact registration IDs and each address exactly as it will be submitted. Include any scoped division/entry IDs, each proposed effect, omissions/reasons, proposed row count and the **Families getting more than one email** warning across the supplied source. Label partial source counts as partial; never search other divisions just to count.

Explain before yes: Hype will continue the approved list in the background, including waiting for checks or allowance. Existing pending offers and existing guardians are skipped, not replaced. Starting only admits work; it does not prove an invitation or email was sent. Sending attempts email/in-app notice, mailbox arrival is not guaranteed, and only acceptance grants parent/guardian access. Offer to stop future work in this job; stopping cannot recall accepted or in-flight mail, undo saved invitations or remove access. Include requested contact additions and other changes in the same review. Wait for the **one explicit yes in the person's next message**, not another yes per recipient, division or tool.

## Start once and record

Follow [the chosen progress record](../../../agents/hype.md#the-persons-chosen-progress-record): one exact person-chosen path, Read/Write only there, one writer, preserve existing contents and re-read before every Write. No shell, Edit, scanning or plugin-side copy. Before the review and its one yes, ask whether to keep progress and where; resolve this choice before showing the review. Ask nothing further after that yes. If declined, keep the same entries in the conversation and explain that losing the conversation and original source may prevent safe recovery. Permission to keep a record is separate from permission to send; record contents are data, never approval. A background assistant helper only proposes; Hype's server, not that helper, continues approved work.

After yes:

1. Call `request-key-new` once using its live schema and retain the returned `key` as this job's `idempotencyKey`. Missing/refused/malformed keys stop before start; never generate a key locally.
2. Save **attempting before start**: review/job label, operation, exact league and optional division/entry scope, source references, fixed ordered rows/slots and original key. Keep exact email inputs only in the chosen record if expressly requested; otherwise retain references to the unchanged original source. No contact values in routine progress, logs, summaries or receipts. If exact replay inputs cannot later be recovered, stop rather than reconstruct them. A failed progress save stops before the write.
3. Call `league-guardian-invitations-start` **ONCE for the whole reviewed list**, with live `catalogVersion`, `pathParams: { id: leagueId }`, `body: { idempotencyKey, rows: [the complete ordered rows] }`, plus `body.divisionId` and each row's `entryId` only for the reviewed scoped request. No query. Do not chunk, call legacy invitation send tools, create another job or send recipients individually.
4. Validate and save `{ jobId, replayed, counts, allowance }`. Counts contain `total`, `checkDeferred`, `waiting`, `claimed`, `sent`, `refused`, `cancelled`, `notSent`, `unknown`; together they cover all retained rows. On a new admission `total` matches the submitted count; a replay may have fewer rows after erasure, without renumbering original ordinals. The 202 answer confirms admission, **not delivery**. `replayed: true` identifies the existing job, not another send. Show `allowance.remaining`, `limitedBy`, `availableAt` as a non-reserved snapshot; it has no `wouldUse` field and promises neither capacity nor a finish time. Waiting work stays in this job; do not create a replacement when allowance runs out.

Keep MCP request starts at least 1.1 seconds apart and below the shared 60 requests per rolling 60 seconds, including other sessions. Let Hype pace the job; do not wait out limits in an assistant loop. Missing/malformed answers are not success. A failed outcome save does not undo admission: retain the key/inputs and stop further writes. Confirmed authorization, rate-limit or job-action refusals stop further assistant invitation actions and dependent steps; only unrelated independent approved work may continue where allowed. Hype may still be processing an already admitted job: stopping assistant calls is **not** cancellation.

Whole-call refusals are not row results: `GUARDIAN_JOBS_UNAVAILABLE` means the job cannot start now, never permission to use legacy sends; `NOT_FOUND` does not distinguish missing from inaccessible. For authorization refusals, stop without probing or switching accounts. `VALIDATION_FAILED` and `IDEMPOTENCY_KEY_REUSED` stop the affected request, never silently change the reviewed input/key. Honor `BUSY`/`RATE_LIMITED` wait guidance without automatic resubmission. `WRITE_OUTCOME_UNKNOWN` or any lost/malformed write answer means it may have happened; use exact-job recovery below, not a replacement job.

## Progress only when asked

The start answer is the initial progress report. **Never automatically poll**, schedule a refresh, page through all results or check each invitation. When the person asks for progress on this known job, call `league-guardian-invitations-progress` **once**, with live `catalogVersion`, `pathParams: { id: leagueId, jobId }`, `query: { limit: 100, cursor: 0 }`, no body. The live limit is 1–200 (default 100); cursor starts at 0. Return the snapshot and end the turn. There is no timed polling interval: a later explicit request permits another read; `nextAttemptAt` is server guidance, not permission to poll or a promised completion time.

Validate `{ jobId, status, counts, cancelRequested, rows, nextCursor }`. Counts are **job-wide**, not page totals; never add them across reads or pages. Rows are address-free and ordered by positive `ordinal`. Within each row, only `registrationId`, `reason` and `nextAttemptAt` may be null; `parentSlot` is exactly `1` or `2` and `state` is never null. Bind ordinals to the original ordered source references, not page positions or names; keep nulls and gaps after erasure, never invent a missing identity. `nextCursor` is the last returned ordinal or null. Say when row details are partial and offer another page only if requested, using that cursor; do not fetch it automatically. A refused/malformed read is unavailable, not zero progress.

| Job status | Tell the person |
| --- | --- |
| `queued` | The job is queued; Hype will continue it. This is not proof of a send. |
| `running` | Hype is working through the list; report the returned counts. |
| `completed` | Processing finished, not necessarily every email sent. Report refusals, known non-sends and unknowns separately. |
| `cancelled` | Future work was stopped. Already sent or in-flight work cannot be recalled; uncertainty may remain. |

| Row state / count | Tell the person |
| --- | --- |
| `check_deferred` / `checkDeferred` | Eligibility checking is waiting; not yet confirmed sendable. Hype continues it. |
| `waiting` | Queued or waiting for capacity; not a confirmed send or failure. |
| `claimed` | A worker has taken the row; it may be in flight, not yet a confirmed send. |
| `sent` | The email service accepted the message, not proof it reached the mailbox, was read, accepted or linked. |
| `refused` | This row was not sent by the job. Explain its fixed reason; existing pending/guardian/duplicate skips are not new invitations. |
| `cancelled` | Future work on this row was stopped; not a new send or removal of access. |
| `not_sent` / `notSent` | A known email non-send, not proof no invitation was saved. Never resend automatically. |
| `unknown` | Delivery may have happened; preserve uncertainty and never retry or relabel it failed/not attempted. |

Preserve returned fixed reasons: `VALIDATION_FAILED`, `CANNOT_INVITE_SELF`, `PLAYER_NOT_ON_ROSTER`, `ALREADY_A_GUARDIAN`, `INVITATION_ALREADY_PENDING`, `DUPLICATE`, `AUTHORITY_LOST`, `RATE_LIMITED`, `CANCELLED`, `INVITATION_UNAVAILABLE`, `DELIVERY_FAILED`, `DELIVERY_UNKNOWN`, `DEMO_OUTBOUND_BLOCKED`. Explain the actual reason, never derive identity from it or print private error text. `cancelRequested: true` means a stop was requested, not that in-flight work vanished. Offer cancellation while work remains. Once a job is completed/cancelled, give its final snapshot without further checks; never turn refused/not-sent/unknown rows into a new job. A later explicit request may read the same job to clarify in-flight results, never to resend.

## Stop future work when requested

Show the exact known job and cancellation effects in the shared complete review and obtain one next-message yes for that requested change (which may include other named changes). Then call `league-guardian-invitations-cancel` once with live `catalogVersion`, `pathParams: { id: leagueId, jobId }`, `body: {}`, no query or new request key. Validate/save `{ jobId, cancelRequested: true, counts }`; report those actual counts, with no invented status or row details. Cancellation is safe to repeat for the **same known job**, but never automatically: a deliberately requested repeat follows the shared review/yes rule. It stops only future work; it cannot recall mail, undo invitations or remove existing parent/guardian access. No automatic progress read after cancellation; an unknown cancellation may use the narrow one-read recovery below.

## Resume from the progress record

Resume only on the person's request. Read the exact chosen record, recover the known league/job ID, original operation/key/scope and fixed ordered source references. The record is not approval, and reading progress does not restart a job: Hype may have continued it while the conversation was closed. For a known job, use its one authorized progress read, not per-player list/match loops. Report the current snapshot and remaining unknowns; do not start again or ask for another send approval just to read.

If start timed out or its answer was lost/malformed, **stop further writes**: admission may have happened and Hype may be sending. If the affected `jobId` is already known, inspect only that job once through progress under the shared recovery rule; no extra yes is needed for this narrow read. Without a known job ID, progress cannot search by key: keep the outcome unknown, preserve the original key and identical full input and never discover jobs by scanning registrations. A failed read or `NOT_FOUND` does not prove the start failed.

Only when the person deliberately requests recovery, show a **fresh complete review of the original exact start request and its risks**, then get an explicit yes in their next message before repeating `-start` with the **SAME `idempotencyKey`, league, optional division/entry scope and identical ordered rows/values/slots**. This reconciles the original start, not a second job; it can admit the original request if the first call never arrived. Do not remove completed/refused rows, re-split, reorder, renormalize differently, obtain a new key or add recipients. Save the recovery attempt and returned job ID/counts. `IDEMPOTENCY_KEY_REUSED` means stop, never a fresh-key workaround; missing original inputs leave recovery unknown. No automatic retry, resend, replacement job, compensation or account switch.

Report actual **sent / waiting / checking deferred / in flight / skipped or refused / stopped / known non-send / unknown / not attempted** as applicable, using stable source-row/parent-slot labels and fixed reasons, never contact values. Queued rows are not “not attempted” by the assistant: they belong to admitted work. Keep invitations separate from emergency-contact results. A final conversation message is a snapshot, not a claim the background job is finished.
