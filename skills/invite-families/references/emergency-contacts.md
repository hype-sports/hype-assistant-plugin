# Same-row emergency contacts, one team table at a time

After the invitation step, prepare contacts from the **same source rows and confirmed registration IDs**, not a new contact search. This is a separate review and approval: the invitation job's yes never authorizes contact writes. Follow [One yes for one reviewed table](../../league-setup/references/reviewed-batch.md), with the narrower add-only and no-automatic-retry boundaries here. Never apply invitation batch sizes, batch keys or league-wide approval to contacts.

## Pair each registration with its exact roster entry

Discover the live schemas for `my-home-entities-list`, `team-seasons-list` when needed, `team-roster-contact-status`, `team-roster-list`, `team-player-emergency-contacts-read` and `team-player-emergency-contacts-add`. Missing or refused tools block the affected contact step, not permission to guess or switch to whole-list update. Use the [Teams reference](../../manage-my-team/references/reference.md) for authorized team/season selection. A league role or successful invitation does not grant contact access.

For each confirmed team in the selected league, call `team-roster-contact-status` **once per team**, with live-schema `catalogVersion` and `pathParams: { id: teamId }`, no query/body. Its `entries` contain `entryId`, nullable `registrationId`, `source`, `contactCount` and `linkedParentCount`; these are IDs/counts, not contact details or permission to write. Pair a source registration **only when the exact `registrationId` and `entryId` occur on the same returned row**. Read that team's `team-roster-list` for the selected season and confirm the paired `entryId` is the requested current player row's `id` before contact reads. Never substitute `playerProfileId`, a person's ID or the registration ID as `entryId`.

A missing/null/ambiguous pairing or `NOT_FOUND` leaves the source row out: list **“not on a team yet — no visible paired roster entry”**, not a claim that the player is absent everywhere. An entry missing from the requested current roster is also skipped. Never join by name, nickname, birth date or row position, and never retry another ID type. Readable rows may be limited; do not call a partial list a complete roster or scan other teams to guess a match.

## Read first and prepare only missing contacts

Read `team-player-emergency-contacts-read` separately for each paired player using `pathParams: { id: teamId, entryId }`, no query/body. Check the live `contacts`, `source` and `canEdit`, not just status counts. Omit family-managed contacts and `canEdit: false` rows, explaining why. A failed or malformed required read stops preparation; hidden information is not an empty list. Linked parents' own details are read-only, not contact-import inputs.

- Build each player's candidates from **both Parent 1 and Parent 2** in the same sheet rows. Required fields are `firstName`, `lastName` and a valid `phone`; `email` is optional/null under the live schema. Ask for missing/ambiguous values or skip just that parent's contact and list the reason, especially **missing phone**. Never invent a number, country, name split or relationship. This workflow leaves relationship columns out; invitation success or a supplied email does not supply a missing phone.
- Compare candidates against existing contacts and earlier candidates for that player using **nonempty phone digits OR lowercased, trimmed email**. Add only missing contacts. Deduplicate repeated source rows for the same exact roster entry without losing source references. Existing matches remain untouched; never correct their names, phones, email or relationship through this import. Conflicting details or two different people sharing a matching value need clarification or an explained omission, not a guessed merge or last-column-wins. An invitation skip does not by itself establish a contact duplicate, and a shared address on different players is not a cross-player contact duplicate.
- Keep every existing contact. Never remove, clear or replace a list, edit registration/sign-up contacts, or use `team-player-emergency-contacts-update` as a fallback, even if add is unavailable. Explain `signup_not_shown`: sign-up contacts exist but are hidden here; a new nonempty coach list shows instead of the sign-up fallback without deleting it. Review that effect, never harvest hidden values. Family contacts always take precedence.
- Respect at most **20 contacts per call and 20 total staff contacts** after additions, as the live tool requires. Do not drop existing contacts to make room. Leave an over-limit row out and explain it rather than partially saving an unreviewed subset.

### Check one supplied sign-up contact when asked

Use `team-player-emergency-contacts-match` only for one exact candidate the person supplied and the already authorized player screen where sign-up fallback is shown. Discover its live schema: `pathParams: { id: teamId, entryId }`, `body: { email }` **or** `body: { phone }`, never both, no query. It returns only `{ matchesSignupContact: true/false }` when the underlying authorized screen uses sign-up fallback (the normal assistant read labels it `signup_not_shown`). Elsewhere it returns the normal minimized contact answer without `matchesSignupContact`. Missing that field means unknown/not applicable, not false. Never return hidden sign-up values, guess candidates, scan/batch addresses, put contacts in query strings or retry automatically.

A match checks sign-up data, not whether an intended coach contact already exists; it cannot prove saved additions, invitations or guardian access. Keep add-only decisions tied to the authorized contacts read and the explicit reviewed effect on sign-up fallback. This optional requested read never becomes an automatic per-parent probing loop or a reason to fetch hidden values.

## Review and approve each team table

Show one complete numbered contacts table for **one confirmed team and season**, with at most **50 write rows** per page. Each player's combined missing Parent 1/Parent 2 additions are **one write row**, not two writes. If nothing is missing, list that player as already present/skipped, not a save. More than 50 players needs separately reviewed pages, each with its own yes; a table never covers another team.

Include table/team/season labels and IDs, source sheet/row/parent references, exact `registrationId` and paired `entryId`, intended additions, expected added/skipped counts and the add-only effect. List omitted parent contacts and source rows separately with reasons. Show contact values only in this expressly requested immediate contact review where needed; prefer stable unambiguous source-value references without repeating addresses or phones. If exact inputs cannot be safely and uniquely reviewed, leave the action out. Never put contact values in summaries, logs, reports or unrelated messages; never include birth dates. Follow [own-files privacy](../../league-setup/references/own-files.md) for expressly requested storage, not an automatic import copy.

Explain that existing contacts stay unchanged and matching contacts are skipped; saving contacts sends no invitation and grants no guardian access. Ask for the table's own explicit yes in a **later turn**, naming the table, team and write count, under the shared rule. No per-parent approval is needed inside that exact table. Any changed target, value, order, count or effect requires complete revised review and a new yes.

## Write once, read back, then continue

Re-read each player's authorized contacts immediately before its approved write and compare with the reviewed state. Changed state, family takeover, lost access or a failed read stops the **whole table**, not just that row. Call `team-player-emergency-contacts-add` one row at a time in approved order with live-schema `catalogVersion`, `pathParams: { id: teamId, entryId }`, `body: { contacts: [the exact approved missing contacts] }`, no query or retry key. Never call `request-key-new` for contacts. Keep request starts at least 1.1 seconds apart and below the shared 60 MCP requests per rolling 60 seconds, including reads and other sessions' usage.

After a confirmed add reply, compare `{ added, skipped }` against the reviewed counts. Unexpected counts stop the table; they do not identify which contact was saved. For **each confirmed contact write**, read `team-player-emergency-contacts-read` on the same team/entry before the next write. Check that the intended additions are visible and existing contacts remain unchanged. Counts alone, an invitation receipt or a sign-up candidate match are not proof of the saved contacts. A failed/noncomparable readback, hidden result or family takeover stops remaining writes; retain the confirmed reply and mark verification unresolved rather than complete.

On any refusal (including a rate limit), interruption, timeout, malformed/lost reply or `WRITE_OUTCOME_UNKNOWN`, stop all remaining writes. **No automatic retry**, including the shared rule's short-wait resubmission: this skill is stricter. Contact add has no replay key; never reuse an invitation key, resend to check, compensate, switch accounts or infer failure from an unknown outcome. Do not read automatically after an unknown write; tell the person it may have happened, direct them to the player's screen in Hype and ask before a separate fresh read. A current read cannot prove the earlier call's outcome.

Record table/source labels, exact team/registration/entry IDs, operation, attempted/not attempted, returned counts and readback status without contact values in routine progress. Keep **done / skipped / failed / unknown / not attempted** separate for contacts and invitations. A later requested continuation needs fresh authorized reads, a fresh remainder table and a new later-turn yes; a progress record is not approval. Set unknown attempts aside for deliberate recovery rather than silently replaying them. Invitation batch replay never recovers a contact write.
