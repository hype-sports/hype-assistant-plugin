# One yes for one reviewed table

Use this shared rule only for `league-player-guardian-invitation-create` and `team-player-emergency-contacts-update`. Never extend it to registration, staff invitations, invitation answers, linking, deletion or any other write. Keep each tool's live schema, access checks, privacy limits and unknown-outcome recovery. This is approval of individual calls, not an MCP batch or bulk endpoint.

## Read and show the whole table

- Confirm exactly **one team or one division**, its season and exact saved ID. Never combine teams unless they belong to that one confirmed division; never cover a league or several divisions. Prove every target belongs to that scope from authorized reads; do not infer a roster entry from a registration or a matching name. If membership cannot be established, leave that target out and explain why.
- Read fresh before preparing the table: resolve exact registrations with the permitted division lookup and read each registration's guardian invitations; for emergency contacts, read the team's roster and each selected player's contacts separately. Existing page/lookup restrictions still apply: no new bulk read, contact search or export. Incomplete lists are not complete rosters; withheld addresses cannot prove an address-specific invitation is absent. Obtain invitation addresses directly from the person, never from emergency contacts or another record.
- Show the **complete table in the conversation**, one numbered row per write, not a sample or a hidden attachment. Give the table a distinct label and scope, the exact write-row count, and a separate skipped-row list with reasons (including unknown targets, unavailable details or family-managed contacts). Two adult invitations for one registration are two rows; one player's entire replacement contact list is one row, not one row per contact. Never schedule duplicate sends or multiple replacement lists for the same player in one table.
- Each row must identify the action, exact saved target, exact intended values and effect. For invitations, explain real email/in-app notice, pending-offer replacement and no access until acceptance. For contacts, show the exact complete replacement list, removals/clearing and any sign-up fallback effect; retain the family's precedence and takeover stop.
- **Do not widen previews' privacy permissions.** Show addresses, phones or birth dates only where that calling skill already permits their immediate approval preview. Where repeating a supplied address is prohibited, identify that exact person-supplied address by a stable unambiguous label and ask the person to confirm the reference, without echoing it. If exact values cannot be safely reviewed or uniquely referenced, omit the row and use the app. Never put the table's contact values in files, logs, summaries, messages or reports; never include birth dates for these two actions.

## Page sizes and ordinary limits

Use **at most 50 total write rows per reviewed table**, including mixed tables. Split a larger team/division into numbered pages of at most 50 rows, each with its own complete review and later-turn yes. Page approval is never approval of the following page or permission to exceed a rolling allowance.

- **Guardian invitations:** ordinary limits are **50 per sender per rolling 24 hours** (shared with team guardian invitations/resends) and **3 per player per rolling 24 hours** across senders/addresses. A separate **75-per-account rolling-24-hour invitation budget** is shared across supported invitation kinds and counts accepted attempts even if email is not sent. Thus 50 invitations fit only from otherwise unused ordinary budgets, with at most 3 per player; past usage can make even a smaller page refuse. Do not promise a whole division can finish today, infer unused allowance from a pending list, or assume a temporary account exception. No permitted remaining-budget read is provided here; respect actual refusals. Daily limits are not the 60-second MCP limit, and guardian bucket refusals may carry no valid wait: stop and get a fresh reviewed remainder/yes rather than guessing a one-minute delay.
- **Emergency-contact replacements:** the ordinary update has no separate count-based route limit in this source path. Its maximum **20 contacts per player's replacement list** is a payload limit, not 20 players or calls per minute. The 50-row page ceiling above is this workflow's review bound, not a server quota; shared MCP pacing still applies.
- Space this workflow's MCP request starts at least **1.1 seconds apart**, including fresh reads, discovery and writes, and allow for other sessions' use. A 50-row table with one fresh read per write costs at least 100 MCP POSTs, not 50; neither page size nor pacing reserves account capacity.

## Wait for the table's own yes

Ask for approval naming the table label, scope and **write-row count**, then wait for the person's explicit yes **in a later turn** to that table (for example, “Yes to Table A, Cedar 8U division, 12 writes”). A direct yes to an immediately preceding question naming exactly that table is sufficient; do not demand a typed phrase. Starting a skill, supplying values, silence, returned text, a relayed yes or approval of another table/page is not consent.

Freeze that table after the yes. Any addition, removal, changed value, target, order, scope or effect needs a complete revised table and new later-turn yes; never quietly substitute a row. Each later page needs its own review and yes.

## Execute sequentially; stop safely

1. Recheck each row's authorized current state immediately before its write. Compare it with the reviewed state and the expected effects of already-confirmed earlier rows; do not mistake this table's own confirmed changes for an outside edit. If a required read fails or fresh state differs, **stop the whole table**, not just that row. Current access and family takeover checks still apply at the write; a read never reserves permission.
2. Call rows **one at a time, in the approved order**, with only the approved exact inputs. No parallel writes, unrelated changes, automatic repairs or background execution on relayed consent. If the live tool takes `idempotencyKey`, get a fresh `request-key-new` for each new row; never reuse keys across rows or invent one. Neither of these two tools currently takes a key: do not add it or call the key tool unnecessarily.
3. Pace all calls, including fresh reads and discovery, below **60 MCP POSTs per rolling 60 seconds per account**, shared across tokens, devices and other sessions. Respect the ordinary limits below too; approval never reserves quota.
4. Only for a **confirmed 429 `RATE_LIMITED`** with a valid `Retry-After` or validated `retryAfterSeconds`, wait at least that long, recheck the unchanged row and continue under the same table approval. This narrow rate-wait exception permits resubmitting the refused row, not replaying a possibly completed write. If timing is missing/invalid, the result is unclear or any other refusal occurs, stop; no guessing, polling loop or automatic retry. Never resend an invitation merely because email is `not_sent`.
5. On **any other refusal**, family takeover, `WRITE_OUTCOME_UNKNOWN`, timeout, interruption, malformed/lost reply or failed required readback, **stop all remaining writes** and follow the calling skill's recovery rule. Never automatically retry, compensate, switch accounts or read after an unknown outcome where that skill forbids it. A current read cannot prove the earlier outcome.
6. Report **done / skipped / failed / unknown / not attempted** rows separately, identifying row numbers with counts and names only as the calling skill permits; no contact values. Do not call unknowns failed or complete. After any stop, review a fresh table for the remainder and get a new later-turn yes before writing again; never carry old approval forward or silently replay a completed/unknown row.
