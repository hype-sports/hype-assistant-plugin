# Invitation and emergency-contact safeguards

Use [One review, one yes, all changes](../../../agents/hype.md#one-review-one-yes-all-changes) for consent across the whole requested list. This reference adds tool-specific checks, not a separate approval boundary, page ceiling or team/division limit on that list. Several teams or divisions can be reviewed together only when each exact target is independently identified and authorized. One yes never combines server calls into an invented bulk endpoint.

For the live league invitation preview/send tools, follow [Invitation jobs and safe progress](../../invite-families/references/reviewed-job.md). For contacts from those same source rows, also follow [Same-row emergency contacts](../../invite-families/references/emergency-contacts.md): add-only, with no whole-list update fallback.

## Choose the contact tool before review

Read the live schemas first. For add-only rows use `team-player-emergency-contacts-add`: it adds missing contacts and never changes or removes existing ones. For edits/removals use `team-player-emergency-contacts-update`, labeled **replaces the whole list**, preserving every unchanged contact from a fresh authorized read and explicitly showing removals or clearing.

Outside invite-families, an update fallback is possible only when add is absent from the live schema, never when add refused. Explain the whole-list effect and show the complete replacement in the shared review before choosing it. Do not switch tools after approval or use replacement to bypass contact matching. The live tool and family takeover checks still decide current rights.

## Resolve exact targets and show all effects

- Confirm team/division, season and exact saved IDs for every target. Prove scope from authorized reads, never matching names or inferred membership. To pair a registration with a team roster entry, use only the same returned `team-roster-contact-status` row's exact `registrationId` and `entryId`. Null, absent or `NOT_FOUND` pairings stay unresolved; no fallback to names, birth dates or another ID type.
- Read current registration invitations for invitation actions and each selected player's roster/contacts for contact actions. Existing lookup/page restrictions remain: no new bulk contact read, search or export. Partial lists are not complete rosters; withheld addresses cannot prove an address-specific invitation is absent. Obtain recipients directly from the person, never another contact record.
- Include every requested write in the shared complete review, not a sample or hidden attachment. Group by team/division for clarity without requesting another yes for each group. Show exact targets, values, effects, notifications, write count and skipped rows/reasons, including family-managed or unresolved contacts. Two adult invitations for one registration are two calls; combine one player's missing additions or full replacement contacts into one contact call. Never schedule duplicate sends or duplicate contact writes for the same player.
- For invitations, explain real email/in-app notices, any pending-offer replacement and no guardian access before acceptance. For contact adds, compare intended additions with existing contacts and earlier candidates in that call using nonempty phone digits **or** lowercased, trimmed email. Show expected added/skipped counts; matches keep their existing values. If skipping does not meet the request, omit that action and explain why, never replace to evade a match. Explain sign-up fallback effects and retain family precedence.
- Preserve the calling skill's privacy limits: show private values only where its immediate review permits them; otherwise use stable, unambiguous person-supplied value references. If exact input cannot be safely identified, omit the action and use the app. An invitation review shows each address being invited exactly as it will be sent. No contact values in logs, summaries or reports; no birth dates for these invitation/contact actions. Follow [own-files privacy](own-files.md).
- For individual `league-player-guardian-invitation-create` calls, count each normalized address's invitations across the whole supplied league source, not just a team/division group. Show **Families getting more than one email**, with permitted address references, covered player rows and total emails, distinguishing **already sent** from **planned, not yet checked**. Exclude pending-address skips and omitted rows. Each registration gets its own invitation by design; never merge siblings. If only part of the source was supplied, label the count partial; never read other divisions just to count. Changes to that list return to the shared review.

## Invitation allowance

Use only the id of the league being acted on, never another league's, archived or not. For a requested allowance check or individual parent/guardian invitations, use `league-invitation-allowance-get` with live `catalogVersion`, league `pathParams: { id }`, no body/query. Invitation batch jobs instead use their required preview's `allowance`; do not add this extra read.

Show returned `remaining`, `limitedBy` and `availableAt`. At zero capacity name the limiting scope/opening time, never guess a reset. Batch preview `wouldUse` is proposed usage, not remaining capacity: add usage across the job, never add remaining amounts. If proposed usage exceeds the first preview's remaining amount, explain that the job may stop at the allowance and require a requested resume. Snapshots reserve nothing; other sessions, player limits and shared budgets still apply. On requested resume use current allowance, never poll, switch accounts or wait out a daily cap on old approval.

## Server limits and pacing

- Individual guardian invitations remain limited to **3 per player per rolling 24 hours**, across senders and addresses, plus current sender/shared capacity. Review size is not sending capacity. Follow a rate refusal's wait guidance without automatically resubmitting it; a requested resumed remainder needs the shared review and one new yes.
- Emergency-contact calls accept at most **20 contacts**; add also refuses when the resulting staff list would exceed **20 total**, with no partial save. These are contacts, not players or calls per minute. Add uses `pathParams: { id: teamId, entryId: rosterEntryId }`, no query, and `body: { contacts: [...] }` with required `firstName`, `lastName`, `phone` and optional/null `email`, plus other fields only as allowed by the calling skill and live schema.
- Add skips matching phone digits or normalized email, including matches earlier in the same call. A repeat against unchanged state skips rather than updates; `{ added, skipped }` gives counts, not identities or a replay receipt. There is no retry key: matching never permits retrying an unknown outcome.
- Keep MCP request starts at least **1.1 seconds apart**, including reads, discovery, key requests and writes, and stay below **60 MCP POSTs per rolling 60 seconds per account**, shared across tokens, devices and sessions. A list with one read per write costs at least twice its write count. Pacing and approval reserve no quota.

## Execute and verify each approved call

Recheck each target's authorized current state before writing. Compare against the reviewed state plus expected effects of earlier confirmed actions, not an outdated snapshot. New values/effects require revised review; failed or refused prerequisites block their dependent actions, not other approved independent work.

Call once per action in approved order. Every new individual guardian invitation gets its own fresh `request-key-new` key as `idempotencyKey`; retain it with exact inputs through any uncertainty. Never share keys, invent them or replace them after a lost reply. Missing keys block the send. Contact add/update take no key: do not request or add one.

After contact add, compare actual `{ added, skipped }` with the review before continuing dependent work. Unexpected counts do not identify which contacts were saved: inspect authorized state, report the mismatch and mark verification unresolved; never repair silently. Report skips separately from added contacts. Family takeover refuses that contact change, not unrelated approved targets.

For individual league invitations, confirmed `ALREADY_A_GUARDIAN` means **Already a parent/guardian, skipped**, not a new send. Never resend merely because email is `not_sent` or `unknown`. Handle every other confirmed refusal, unknown answer and requested recovery under the shared rule and the calling skill's exact-key contract. Unknown outcomes mean the write may have happened: stop writes, read only the affected item once through a supported authorized read and report its state; without such a read, keep it unknown rather than scan wider lists; current state alone is not a historical receipt.
