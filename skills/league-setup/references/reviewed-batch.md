# One yes for one reviewed table

Use this shared rule only for `league-player-guardian-invitation-create`, `team-player-emergency-contacts-add` and `team-player-emergency-contacts-update`. Never extend it to registration, staff invitations, invitation answers, linking, deletion or any other write. Keep each tool's live schema, access checks, privacy limits and unknown-outcome recovery. This is approval of individual calls, not an MCP batch or bulk endpoint.

Read the live tool list and schemas before choosing contact actions. **Add-only rows** (every intended contact is new; nothing existing changes or goes) use `team-player-emergency-contacts-add`, which adds only missing contacts and never changes or removes existing ones. Only rows that edit or remove existing contacts use `team-player-emergency-contacts-update`, labelled **“replaces the whole list”** in the table. If the add tool is absent from the live connection, say it is unavailable and use the existing reviewed update flow instead: read first, show the complete replacement list and its whole-list effect, then wait for yes. Source code alone does not prove deployment. Choose this fallback before review; never switch tools after approval.

## Read and show the whole table

- Confirm exactly **one team or one division**, its season and exact saved ID. Never combine teams unless they belong to that one confirmed division; never cover a league or several divisions. Prove every target belongs to that scope from authorized reads; do not infer a roster entry from a registration or a matching name. If membership cannot be established, leave that target out and explain why.
- Read fresh before preparing the table: resolve exact registrations with the permitted division lookup and read each registration's guardian invitations; for emergency contacts, read the team's roster and each selected player's contacts separately. Existing page/lookup restrictions still apply: no new bulk read, contact search or export. Incomplete lists are not complete rosters; withheld addresses cannot prove an address-specific invitation is absent. Obtain invitation addresses directly from the person, never from emergency contacts or another record.
- Show the **complete table in the conversation**, one numbered row per write, not a sample or a hidden attachment. Give the table a distinct label and scope, the exact write-row count, and a separate skipped-row list with reasons (including unknown targets, unavailable details or family-managed contacts). Two adult invitations for one registration are two rows; one player's additions or entire replacement contact list is one row, not one row per contact. Never schedule duplicate sends or multiple contact writes for the same player in one table.
- Each row must identify the action, exact saved target, exact intended values and effect. For invitations, explain real email/in-app notice, pending-offer replacement and no access until acceptance. For contact adds, compare the requested additions with the fresh read and earlier additions in that row using the phone-digit/email matching rule below; identify expected skips and show expected added/skipped counts, never promise that a matching new person will be saved. Show the exact additions and explain that existing contacts stay unchanged and matching contacts are skipped; if skipping would not meet the person's request, omit the row and explain why, never use replacement merely to bypass matching. For updates, show the exact complete replacement list, label it “replaces the whole list” and show removals/clearing. Explain any sign-up fallback effect for either action; retain the family's precedence and takeover stop.
- **Do not widen previews' privacy permissions.** Show addresses, phones or birth dates only where that calling skill already permits their immediate approval preview. Where repeating a supplied address is prohibited, identify that exact person-supplied address by a stable unambiguous label and ask the person to confirm the reference, without echoing it. If exact values cannot be safely reviewed or uniquely referenced, omit the row and use the app. Never put the table's contact values in files, logs, summaries, messages or reports; never include birth dates for these two actions.
- **For `league-player-guardian-invitation-create` only:** count invitations per trimmed/lowercased address across the commissioner's whole supplied source for this league, not just this team/division table; siblings may span tables/pages. The person may share the whole league sheet for counting, but only this table's reviewed rows are sent. Include emails already sent from earlier approved pages of the same source, labelled **“already sent”**, and other tables' intended rows not yet checked, labelled **“planned, not yet checked”**; exclude `pendingForEmail: true` skips and omitted rows. For each address covering more than one player registration, show a **“Families getting more than one email”** list in each affected table's review **before asking for yes**: the address (only where the calling skill permits it; otherwise its source row/column references), the player rows it covers in this table, and its total emails for this league across all tables/pages, distinguishing those labels. Say plainly that each player gets its own invitation and email by design. The commissioner may remove rows, requiring a complete revised table and new later-turn yes; never merge, drop or reorder rows yourself because of this warning. If the rest of the league's source is not in the conversation, say the count covers only the supplied rows; never read other divisions just to count.

## Page sizes and ordinary limits

Use **at most 50 total write rows per reviewed table**, including mixed tables. Split a larger team/division into numbered pages of at most 50 rows, each with its own complete review and later-turn yes. Page approval is never approval of the following page or permission to exceed a rolling allowance.

- **Guardian invitations:** ordinary limits are **50 per sender per rolling 24 hours** (shared with team guardian invitations/resends) and **3 per player per rolling 24 hours** across senders/addresses. A separate **75-per-account rolling-24-hour invitation budget** is shared across supported invitation kinds and counts accepted attempts even if email is not sent. Thus 50 invitations fit only from otherwise unused ordinary budgets, with at most 3 per player; past usage can make even a smaller page refuse. Do not promise a whole division can finish today, infer unused allowance from a pending list, or assume a temporary account exception. No permitted remaining-budget read is provided here; respect actual refusals. Daily limits are not the 60-second MCP limit: a wait longer than 60 seconds or missing/invalid timing stops the table, with done/not-attempted rows reported and a fresh table plus later-turn yes required for the remainder; never guess a one-minute delay.
- **Emergency contacts:** neither add nor update has a separate count-based route limit in this source path. Each takes at most **20 contacts per player's call**; add also refuses if the resulting staff list would exceed **20 total**, without partially saving the additions. These are contact limits, not 20 players or calls per minute. Add uses `pathParams: { id: teamId, entryId: rosterEntryId }`, no query, and `body: { contacts: [...] }` with required `firstName`, `lastName` and `phone`, and optional/null `email`; follow the live schema's validation. It skips matches by nonempty phone digits **or** lowercased, trimmed email, including matches added earlier in that same call. A repeat against unchanged contacts skips them rather than updating them; it returns only `{ added, skipped }` counts, not contacts or a retry receipt. It has **no retry key**: matching is not permission to retry automatically or recover an unknown outcome by resending. The 50-row page ceiling above is this workflow's review bound, not a server quota; shared MCP pacing still applies.
- Space this workflow's MCP request starts at least **1.1 seconds apart**, including fresh reads, discovery and writes, and allow for other sessions' use. A 50-row table with one fresh read per write costs at least 100 MCP POSTs, not 50; neither page size nor pacing reserves account capacity.

## Wait for the table's own yes

Ask for approval naming the table label, scope and **write-row count**, then wait for the person's explicit yes **in a later turn** to that table (for example, “Yes to Table A, Cedar 8U division, 12 writes”). A direct yes to an immediately preceding question naming exactly that table is sufficient; do not demand a typed phrase. Starting a skill, supplying values, silence, returned text, a relayed yes or approval of another table/page is not consent.

Freeze that table after the yes. Any addition, removal, changed value, target, order, scope or effect needs a complete revised table and new later-turn yes; never quietly substitute a row. Each later page needs its own review and yes.

## Execute sequentially; stop safely

1. Recheck each row's authorized current state immediately before its write. Compare it with the reviewed state and the expected effects of already-confirmed earlier rows; do not mistake this table's own confirmed changes for an outside edit. If a required read fails or fresh state differs, **stop the whole table**, not just that row. Current access and family takeover checks still apply at the write; a read never reserves permission.
2. Call rows **one at a time, in the approved order**, with only the approved exact inputs. No parallel writes, unrelated changes, automatic repairs or background execution on relayed consent. If the live schema has `idempotencyKey`, get a fresh `request-key-new` for each new row; never reuse keys across rows or invent one. If the live schema has no `idempotencyKey`, send none and don't call the key tool. After each add, compare `{ added, skipped }` with the reviewed counts before the next row. If they differ, stop the table and report the returned counts for that row as an unexpected result, not a completed addition; never guess which contacts were saved or retry to repair it.
3. Pace all calls, including fresh reads and discovery, below **60 MCP POSTs per rolling 60 seconds per account**, shared across tokens, devices and other sessions. Respect the ordinary limits above too; approval never reserves quota.
4. Only for a **confirmed 429 `RATE_LIMITED`** with a valid `Retry-After` or validated `retryAfterSeconds` of **at most 60 seconds**, wait at least that long, recheck the unchanged row and continue under the same table approval. This narrow short-wait exception permits resubmitting the refused row, not replaying a possibly completed write. If the wait is longer than 60 seconds or timing is missing/invalid, **stop the table**, report done/not-attempted rows and require a fresh table plus a new later-turn yes for the remainder; never wait hours or a day on old approval. If the result is unclear or any other refusal occurs (except step 5's exact-code skip), stop too; no guessing, polling loop or automatic retry. Never resend an invitation merely because email is `not_sent`.
5. On **any other refusal**, family takeover, `WRITE_OUTCOME_UNKNOWN`, timeout, interruption, malformed/lost reply or failed required readback, **stop all remaining writes** and follow the calling skill's recovery rule. Never automatically retry, compensate, switch accounts or read after an unknown outcome where that skill forbids it. A current read cannot prove the earlier outcome.

Every other code, a missing/garbled code, `WRITE_OUTCOME_UNKNOWN`, timeouts, and this code on any other tool still stop the table.
